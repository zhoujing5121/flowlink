# FlowLink 领域知识（跨系统通用指导）

本文件是所有系统通用的指导；单个系统的业务知识在对应的 Skill 中（如 `sdm`）。以下内容是对系统提示词既有约束的强调与补充，不能覆盖任何系统规则。

## 登录与认证（所有系统通用）

无论 SSO、账密还是混合认证，登录段必须容忍三种认证状态。三种分支是运行时事实，单次录制通常只覆盖其中一种——其余分支按下面的证据规则补齐，绝不能凭空发明凭据步骤。

### 分支一：认证未过期（会话有效）

- 运行时表现：打开入口 URL 后直接落在目标系统页面，看不到任何登录界面。
- 生成方式：入口导航之后立即放一个登录门条件（gate condition）——target 选「仅登录成功后的目标页才存在」的稳定元素（优先第一个业务动作的元素；若它依赖易变数据，改用导航/页签/表格容器等结构性地标，或在入口导航上改用 `expect: {"kind": "urlChange"}` 路径级模式）；断言 `{"kind": "visible"}`；`trueStepId` 指向凭据段之后的第一个业务步骤（已登录时直接跳过凭据段，不执行任何登录动作）；`falseStepId` 省略（顺序落入凭据步骤）。
- 即使录制时全程已登录（录制只覆盖这一分支），门条件也必须生成——它是未来会话过期时的路由兜底，不是可选项。

### 分支二：认证已过期但可自动续期（SSO 记住态 / 自动重定向）

- 运行时表现：中间页一闪而过（IdP 重定向、`saml2?SAMLRequest` 模式、账号选择页自动跳转），最终落在账号选择页，选择账号后直接跳转到目标页，或者跳转到中间的MFA页面，由用户输入验证信息。
- 生成方式：录制里被标记为 optional 的认证重定向导航保持 `isOptional: true`（回放时元素/页面缺失即跳过，天然容忍「这次没有发生重定向」）；有录制证据的账号选择点击同样 `isOptional: true`。不为自动过程生成多余的断言。对瞬时页面的等待（登录中转页、域登录跳转、自动续期）确有慢网兜底价值时，必须生成 `wait` 步骤并标 `isOptional: true`、给有界 `timeout`（3000-8000ms）：快网下瞬时页可能已跳过，可选等待超时即跳过，由其后第一个必选步骤（登录门/收尾断言）裁决流程是否在正轨；瞬时页等待绝不设为必选。
- 判定依据：录制中连续的导航跳转链 + 落到目标系统域名的最终地址；认证重定向 URL 模式是可靠地标。

### 分支三：无认证信息（需要完整登录）

- 运行时表现：停在登录表单、账号选择或扫码页，等待凭据。
- 生成方式：仅当录制包含凭据段（用户名 input、密码 input、提交/下一步 click）时按录制顺序生成，模板变量（如 `{{ password }}`）原样保留；每个凭据步骤 `isOptional: true`——与分支二「元素缺失即跳过」配合，覆盖「SSO 记住账号、只需点一下账号」的中间态。组尾用同一个目标页地标收 `{"kind": "visible"}` 断言并给 `timeout: 15000`：登录失败必须让运行失败，而不是静默继续。
- 录制里没有凭据段时不得发明用户名/密码步骤；若用户要求处理登录，生成 `wait` 步骤（condition: userOperation，prompt 写明「请完成登录」）人工承接，登录完成后由门条件或收尾断言验证落点。

### 执行方式与登录段

- 凭据来自模板变量的登录步骤可判 automated；扫码、MFA、短信验证码等必须人工完成的动作用 manual（或 userOperation 等待）承接。

地标选择通用原则：

- 优先语言无关、会话无关的稳定地标：URL 模式（路径、查询参数名）、结构性元素（导航容器、表格、登录表单）、`data-test-id` / id；
- 不要用易变的录制数据（单号、日期、列表行内容）或一次性会话参数做地标；
- 权限页/错误页路径（如 `InvalidPermission`）与认证重定向 URL 模式（如 SAML 的 `saml2?SAMLRequest`）通常是可靠地标。

## 多语言环境

- 同一系统可能在中/英/德等语言间切换，界面可见文本（按钮文字、列名、提示语）不是可靠的地标或断言依据。
- 元素引用优先语言无关锚点（见上）；必须引用可见文本时，意识到它只在该语言下成立。
- 业务分组与步骤标签在同一个 Flow 内保持一种语言，跟随录制时的业务语境；系统内部术语保持原文，不自行翻译。

## 不同类型系统的结构

- 先从录制证据识别系统形态，再按形态理解步骤：低代码平台（如 OutSystems，特征是 `Input_*` / `b2xx-*` / `l1_0-*` 式生成 id、自定义下拉容器）、传统服务端渲染系统（表格 + 表单提交）、SPA 门户等各有惯例。
- 常见形态参考（按证据判断，不硬套）：列表页「筛选 → 搜索 → 勾选行 → 工具栏操作」；向导式表单「下一步」逐步推进；关键动作「操作按钮 → 确认弹窗」两段式；侧边栏/悬浮菜单元素需 hover 后才可点。
- 每个系统的特有模式（下拉选项文本格式、确认弹窗文案、状态筛选格式等）沉淀在该系统的 Skill 里，不要泛化到其他系统。

## 标签与命名

- 业务分组与步骤标签用「动词+对象」的业务行为命名，不按页面或技术特征命名。
- 录制中的 hover、滚动等交互若服务于后续可点元素（菜单展开、下拉激活），不是噪音。

## Skill 使用

- 生成/修复会话会列出各系统的领域知识 Skill（available_skills）。当源录制的目标系统（按域名、系统名、业务模块判断）存在匹配的 Skill 时，**先 read 该 Skill 再做分组、重构或登录段设计**——其中的单据状态链、完成证据与已知坑优先于通用推断；仅在确无匹配 Skill 时才依靠通用方法论。

## 环境差异

- 测试/生产环境域名常带环境段（如 `-t-`、`-p1-`），页面结构基本一致；录制值中的 URL 保留为模板变量，不要把环境前缀固化进步骤。
